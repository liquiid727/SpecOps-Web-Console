前面三篇讲了三档 spec 是怎么分的、 agent 是怎么用共享骨架加协调者组织起来的。这篇讲一个更根本的问题：光有 spec 和 agent ，怎么保证它们不会随着时间慢慢跟代码脱节？

有次上线之后，产品在群里问我一个功能的边界条件，我打开对应的 spec ，上面写的规则和代码里实际跑的逻辑对不上——中间有次改动只改了代码，没人回头改 spec 。我照着 spec 回答了产品的问题，答错了，现场又当着人回炉重来一次，那滋味真是一言难尽。

"
spec 最怕的根本不是没人写，是写完了没人管，而且它烂掉了不会喊一声。

那次之后我才想明白，代码写错了，跑起来会报错，会有人发现； spec 写错了，它就安安静静地躺在那儿，等着某个人在某个时刻信任它，然后被它坑一次。

靠自觉去维护 spec ，说白了是在赌自己每次改代码都会想起来回头看看 spec 是不是也该改。这个赌我已经输过一次，不想再赌第二次。而且这个赌局对个人还好，一旦有第二个人一起改代码，赌注就变成了"赌两个人都会记得"，输的概率只会更高不会更低。

真正能解决问题的不是提醒自己要维护，是不维护就过不去——把 spec 和代码是否一致这件事做成一道拦得住人的关卡，而不是一条靠良心的建议。这跟上一篇讲的升级逻辑其实是同一套：靠自觉解决不了的问题，就该靠机制去解决。

我把关卡按流程推进的顺序分成了四级，越往后越严：

1.PR Fast Gate：先做最快的检查——spec 、测试计划这些东西格式对不对，有没有缺必填字段，改动涉及的模块单测过没过、类型检查过没过，追求的就是"快"，几秒到几十秒内出结果，不合格的直接拦在门口，不浪费后面几级的时间。
2.Change Verification Gate：跑一遍这次改动对应的证据，确认关键场景确实测过、结果和 spec 版本对得上，缺证据、缺关键路径测试结果的都会被拦下来，这一级开始要真正跑测试比对结果，成本比第一级高不少。
3.Release Gate：跑全量业务场景测试，涉及性能和并发的关键路径也要过一遍，确保这次改动不会让某个原本正常的场景突然变慢或者出现并发问题。
4.Promote Gate：要求前面所有关卡的结论都指向同一个 spec 版本，没有遗留高风险问题才准发布——本质上是个总账，检查前三关是不是真的都过了，而不是被绕开的。

越到后面，检查的东西越接近"真的要对用户负责"那一层，也越贵，但越贵的关卡，出问题的代价也越大，这笔账算下来是划算的。而且四级递进意味着大部分不合格的改动会在第一级就被拦下来，真正走到第四级、消耗最多资源的，往往是已经在前面几关证明过自己靠谱的改动，整体成本比每次都全跑一遍要低不少。

四级门禁真正接进自动化 CI 流水线之前，我先写了个本地能跑的校验命令，把逻辑先落地验证一遍，确认这套判断规则真的靠谱，不是我关起门来想当然设计出来的一套自嗨规则。命令跑起来之后，会去读这次改动对应的测试计划，把提交的测试结果一条条比对，只要有证据缺失或对不上，直接判定为拦截，不会放行。跑通了打印一行明确的通过标记，跑不通打印拦截外加缺了什么证据——不是"看起来大概没问题"，是有就是有，没有就是没有。

说来惭愧，我自己第一次跑这个命令的时候，是抱着"应该能过"的心态跑的，结果被拦了一次——缺了一份关键场景的测试结果，我自己都没意识到那份证据没补上。被自己写的工具拦下来，说实话有点哭笑不得，但也正是这次经历让我确信这套规则是真的在起作用，不是摆设。

老实交代
规则和本地命令我都已经写完并且能跑通，但眼下这套门禁还没有真正挂到自动化的 CI 流水线上去，现在提交代码它不会自动帮我拦截，得靠我自己想起来手动跑一下。这不是我想藏起来的短板，是设计先跑通、自动化接入放在下一步的正常节奏，没必要装作已经全部搞定了。

之所以敢把这个"没做完"摆出来讲，是因为我越来越觉得，规则和工具先在本地跑顺、验证过判断逻辑没问题，再往自动化里接，比反过来"先囫囵接进 CI 、跑起来再慢慢调规则"要靠谱——后者很容易因为规则本身还有问题，被大家吐槽几次之后就被绕过甚至关掉，那就白折腾了。

规则写得再全，只要它还没成为一道"不过就走不下去"的硬关卡，就还是在赌自觉——我自己就是那个被赌输过一次的人。这些年攒下来的坑，除了这一个，其实还有一份更长的清单，下一篇打算认真列一列。
