# 救命！在被 AI 卷成八爪鱼之前，我先给自己搓了一套"作弊小抄"

昨天晚上，我打开了一个两周没碰的项目。

我看着claude上一次处理的请求：

> "继续实现支付模块吗？"

我盯着屏幕愣了十几秒。

不是因为 AI 不会。

而是……

**我已经忘了我要干什么了！** 烦死了 又是其他的需求要插队处理

于是开始翻 Git、翻 PR、翻聊天记录、翻设计文档。

折腾了四十多分钟。

真正开始写代码，只用了十几分钟。

那一刻我突然意识到一个有点扎心的事实：

**AI 从来不会忘。**

真正记不住的，是我。 脑子啊脑子，你能不能好使一些啊！

唰一下。

几百行代码出来了。

项目甚至还能跑。

以前写一天的代码。

（哈哈，真的变成 Don‘t show me code，Plz BB；）

但真正让我崩溃的，从来不是 AI。

而是我自己。

以前，一个人维护一个项目。

脑子还能装得下。

现在呢？

上午改 Agent。

下午修支付。

晚上写后台。

睡前再去折腾自己的小工具。

一天切四五个项目并且同时并发已经是常态。

他们总是在觉得AI上下文长度不够

可是我感觉先撑不住的是我的脑子

脑子里的第一句话都是：

> "这玩意儿当时到底为什么这么设计？"

> "我接下来应该干啥！"

> "这个 TODO 是准备干嘛？ 这个我还没做么？"

真正贵的，好像已经不是写代码。

而是**重新进入上下文。**

## Spec 的读者已经不是人

原来

Spec、设计文档这些东西。

都是写给团队看的。

新人入职。

同事交接。

架构评审。

大家一起看看。

后来开始大量使用 AI。

我突然发现。

每天读 文档 Spec 最勤快的那个"同事"，

是 Claude。

每次开一个新会话。

第一句话都是：

> "项目背景是什么？"

Cursor 要看。

Codex 要看。

各种 Agent 也要看。

以前文档服务的是人（其实根本没人看）。

现在，它开始有了真正的服务对象 —— AI。

## 我也试过 OpenSpec

不得不说。

OpenSpec 的思路蛮好的。

它几乎把整个软件开发流程都串起来了。

需求。

设计。

实现。

Review。

发布。

每一步都有对应的上下文。

对于团队来说，非常舒服。

但问题也来了。

它有点太完整了（有点费token，执行步骤也相对繁琐）。

完整到我这种同时维护很多项目的人，有时候反而懒得维护（我是懒狗啊）。

流程越完整。

维护成本越高。

于是我就：

> "这次先不更新 Spec，强制跳过，先fix。"

然后 ...

木已成舟

**一份没人维护的 Spec，比没有 Spec 更危险。**

因为 AI 会认真相信它。

而你自己，却已经忘了它是什么时候过期的。我什么时候忘记更新的。

## 所以，我开始给自己搓"作弊小抄"

后来我换了一个思路。

我不再问：

> Spec 应该写什么？

而是问自己：

> 三天后的我重新打开这个项目，如何让Agent知道坐到哪里了，该做什么？

答案其实很简单。

不是所有设计。

不是所有流程。

而是那些最容易忘的东西。

为什么这么设计？

哪些地方千万别改？

现在做到哪一步了？

下一步准备干什么？

于是。

my-Spec 就慢慢出来了。

说白了。

它就是一份写给未来自己的"作弊小抄"。

不用完美。

不用复杂。

不用每个细节都记录。

只需要做到一件事情：

**让我五分钟重新进入状态。**

---

## 三档小抄：从"自己玩"到"要交代"

后来随着项目越来越多。

我发现所有项目，其实都在经历同一条成长路线。

一个人的草台班子。

几个人的小团队。

再到真正需要对客户、对公司负责的产品。

于是慢慢演化出了三档。

**LiteSpec**

一个 Feature 一份小抄。

个人开发、小团队直接开干。

维护成本最低。

上下文也最轻。

**GoalSpec**

团队开始形成固定开发流程。

PRD。

Spec。

Issue。

Review。

Ship。

大家开始围绕同一个 Goal 协作。

流程开始有了闭环。

**EnterpriseSpec**

如果涉及支付、权限、审计这些"改错了真的要出事"的模块。

那就别省了。

QA。

发布证据。

审计记录。

全部留痕。

毕竟真出事故的时候。

总得有人知道去哪抢救。

三档不是三选一。

而是项目长大以后，自然而然会往上升级。
（具体的模式和内容我还在摸索，待方案完善之后再开源出来）

## 然后就是我觉得最重要的一步：别让 Spec 长歪

真正让我头疼的，不是写 Spec。

而是**怎么保证它一直是新的。**

Spec 最怕的不是没有。

而是过期｜错误 ｜遗漏。

于是我又给每一档都设计了一套门禁。

从 PR 检查。

到 Review。

再到发布前终审。

一路检查：

Spec 有没有更新？

代码和 Spec 对不对得上？

会不会 AI 下一次读的时候直接读歪了？

说句实话。

目前这套门禁，本地已经能跑了。

CI 流水线还没完全接进去。

属于典型的：

> "知道救护车该来了，但车还堵在路上。"

我还在慢慢填坑。

## 软件工程新的资产-SPEC

以前的软件工程。

代码是资产。

后来。

文档开始成为资产。

现在我越来越觉得。

现在应该是：

**上下文。**

代码越来越容易生成。

真正难生成的是：

为什么这样设计。

哪些地方不能改。

历史决策是什么。

有哪些坑踩过一次就别踩第二次。

这些，才是一个项目真正的记忆。

也可以称之为

**Project Memory。**

它写给 AI。

也写给未来那个出现生产级事故、需要重新打开项目快速热修的自己。
