# 内置仓库编排流程草案

## 1. 目标

这份文档描述的不是业务 Spec 本身，而是“内置仓库里如何围绕 Spec 组织 Agent 协作与交付流程”。

核心目标：

- 把 Spec 生成、测试生成、执行脚本、CI 接入串成一条统一链路
- 让不同 Agent 有明确职责，而不是混在一起各写各的
- 最终形成从业务意图到可验证交付物的稳定编排流程

---

## 2. 编排定位

可以把这一层理解为：

> 内置仓库的 Agent Orchestration Layer

它不直接等于 Spec，也不直接等于代码实现，而是负责把以下几件事组织起来：

- 项目背景
- 工程规则
- Spec 内容
- Prompt 模板
- Agent 分工
- 执行与审核流程

---

## 3. 角色划分

### Spec Editor

负责编辑、整理和维护标准 Spec 文档。

### Test Editor

负责根据 Spec 生成和维护测试用例，例如 Bruno 测试集合、场景测试、边界测试等。

### CI Editor

负责维护 CI 配置，保证 Spec 驱动出来的测试和流程可以自动执行。

### Execution Editor

负责维护执行脚本、命令入口和编排脚本。

---

## 4. 扩展角色

除了基础编辑角色，还需要加入评审类角色，避免单个 Agent 过度乐观。

建议补充：

- Architect Reviewer：看架构和边界是否合理
- Test Reviewer：看测试覆盖是否真实有效
- Risk Reviewer：从悲观视角检查遗漏、歧义和脆弱点

这样做的目的，是让系统具备“生成 + 审核 + 纠偏”的闭环，而不是只有生成。

---

## 5. 编排输入

一条完整流程至少需要以下输入：

- 项目背景与仓库上下文
- 工程规范 / rules
- 可复用能力 / skills
- spec draft 或标准 spec
- 对应阶段的 prompt 模板

建议目录形态：

```text
/ai/prompts/
  generate_spec.md
  generate_tests.md
  enhance_spec.md
```

---

## 6. 标准流程

```text
业务输入
   ↓
Spec Editor 产出标准 Spec
   ↓
Reviewer 角色做架构 / 风险 / 测试评审
   ↓
Test Editor 生成测试
   ↓
Execution Editor 补齐执行入口
   ↓
CI Editor 接入流水线
   ↓
统一校验通过后提交
```

这个流程强调两点：

- 先有 Spec，再有测试和执行
- 生成之后必须经过评审，不直接进入提交

---

## 7. 关键约束

内置仓库需要把以下约束固化下来：

- 新 feature 必须先有 Spec
- 新接口必须有测试
- PR 必须通过统一检查，例如 `xcli check`

这些约束最好不是只写在文档里，而是逐步沉淀为可执行规则。

---

## 8. 输出物

一次完整编排的结果，至少应该包含：

- 标准化 Spec
- 测试集合
- 执行脚本
- CI 配置
- 评审与校验结果

也就是说，最终交付的不只是“文档”，而是一套可继续执行和验证的工程产物。

---

## 9. 这层编排真正解决什么问题

如果没有这一层，仓库会很快出现这些问题：

- Spec、测试、脚本、CI 各自分散
- Agent 职责不清，输出互相覆盖
- 生成内容缺少审核机制
- 很难形成稳定、可复用的交付链路

因此，这层编排的价值在于：

- 明确角色
- 固化流程
- 建立审核
- 连接 Spec 与工程交付

---

## 10. 一句话总结

`draft/design.MD` 解决的是“Spec 应该怎么设计”，而这份 `draft/task.MD` 解决的是“这个设计在内置仓库里如何被组织、执行、审核和落地”。
