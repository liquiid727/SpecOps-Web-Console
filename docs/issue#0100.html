Implementation Notes

Issue #0100 — Route execution coordinator and one safe fallback — 2026-08-05

Design Decisions

One automatic fallback boundary

The coordinator owns candidate order and creates at most one automatic-fallback Attempt after a machine-classified, clean technical failure. Forbidden failures, disabled fallback, no candidate, and exhaustion end without another automatic Attempt.

Freeze the route input at acceptance

The coordinator deep-copies and freezes candidate/deployment snapshots before asynchronous repository work begins, so caller mutation cannot change fallback order or identity.

Validate stale cancellation before abort

Expected revision is checked inside the task lock before the controller is aborted. A stale cancel request therefore has no runtime side effect.

Deviations

Restart confirmation remains blocked

Completed snapshots can be replayed read-only, but a new coordinator cannot rebuild the executable runAttempt handler for a persisted awaiting-confirmation task. The issue remains blocked rather than claiming unsupported recovery.

Tradeoffs

Keep confirmation recovery for its owning issues

Moving retry context into the coordinator here would duplicate the confirmation/cancel and history-recovery contracts owned by issues 101 and 102. The boundary is recorded as a P1 blocker for those issues to resolve.

Unknown exceptions fail closed

Generic routed execution exceptions now carry unknown side-effect evidence; only explicit pre-execution configuration/secret paths retain clean semantics.

Open Questions

Persisted retry binding

Define which safe, non-secret execution context can recreate a confirmed retry after restart, and how an active running Attempt is marked or recovered after a crash.
