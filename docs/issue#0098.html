Implementation Notes

Issue #0098 — Execution task, Attempt contract, and append-only store — 2026-08-05

Design Decisions

Use session-level in-process serialization

Ambiguity: the spec requires append/revision safety but does not define a cross-process lock.

Choice: serialize all mutations for one session, including delete and public append, and re-read state inside the queue.

Rationale: this makes revision checks and file lifecycle operations atomic within the supported process boundary.

Validate persisted records at runtime

Choice: allow-list Task/Attempt, route, failure, and transition fields before folding or writing.

Rationale: TypeScript types cannot protect recovery from hand-edited or corrupted JSONL.

Deviations

Local waiver remains explicit

The implementation does not claim cross-process locking, fsync/real crash recovery, packaged Tauri, or real Provider/engine evidence because those environments were unavailable and are outside the local in-process proof.

Tradeoffs

Session queue over finer-grained parallelism

A task-only queue would allow more same-session concurrency, but could race with delete and file recreation. Session serialization is simpler and preserves append/delete ordering; unrelated sessions remain independent.

Minimal failure-message redaction

Stable failure code/class/phase are preserved while common bearer, credential, secret, token, key, env, and prompt forms are redacted before persistence. Full external-secret discovery is not inferred from arbitrary text.

Open Questions

Production lock and crash contract

Confirm whether a future packaged or multi-process runtime needs file locks, fsync, and fault-injected restart recovery; add that evidence before removing the waiver.

Independent real-engine boundary

When authenticated Provider/engine and packaged environments are available, rerun the issue Test Spec without substituting synthetic evidence.
