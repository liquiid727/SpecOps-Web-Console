Issue #0090 — Provider secret migration and write-only API — 2026-08-04

Design Decisions

DecisionSerialize credential mutations per Provider

Choice: Reuse the existing application mutation pattern with a provider-scoped lock, then save state and perform keychain cleanup within the serialized operation.

Rationale: Concurrent replacement/delete requests must not expose a half-committed Provider reference or remove the credential selected by a later request.

Deviations

BoundaryKeep platform and packaged evidence blocked

Spec boundary: The local macOS workspace can prove migration, API, memory-store, and rollback seams but cannot prove Windows Credential Manager, Linux Secret Service, or packaged Tauri acceptance.

Implementation: The normalized result records those environments as blocked and does not infer release acceptance from local tests.

Tradeoffs

TradeoffBest-effort rollback across a non-transactional SecretStore

Alternative: Mutate state and let a failed cleanup leave the new reference committed.

Choice: Restore the old reference, remove the new credential, and persist a rollback when old-keychain cleanup fails.

Why: This preserves the prior observable state in the tested SecretStore contract while making any rollback-cleanup failure explicit in logs and QA evidence.

Open Questions

Follow-upReal platform partial-failure semantics

Run Windows/Linux and packaged Tauri canaries, then test a real delete operation that partially succeeds. If the platform API cannot restore an opaque reference, define the recovery contract before removing the blocker.
