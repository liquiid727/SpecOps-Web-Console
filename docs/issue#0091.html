Implementation Notes

Issue #0091 — Unified provider launch resolution and secret redaction — 2026-08-04

Design Decisions

DecisionKeep Provider resolution application-owned

Choice: Reuse the existing `providerLaunchFor` seam for terminal, backend chat, and persistent chat, carrying provider arguments through a transient request field.

Rationale: Profiles, AgentBackends, and the persistent runtime must not resolve or own secrets; only the application can enforce the pre-spawn and redaction boundary.

Deviations

BoundaryUse a transient persistent-runtime argument field

Spec boundary: The existing persistent request exposed env but not the Provider CLI overrides required by OpenAI-compatible connections.

Implementation: `providerArgs` is optional, applied only when the resident process is first spawned, and omitted from serialized domain surfaces. Fake-runtime tests prove this boundary; real Codex acceptance remains unclaimed.

Tradeoffs

TradeoffPreserve resident-process reuse while applying per-session Provider configuration

Alternative: Fall back to cold spawn whenever Provider args exist.

Choice: Pass the transient overrides before `mcp-server` on first spawn, then reuse that process without re-spawning.

Why: This closes the persistent path without writing Provider settings to disk or leaking them into later turns.
