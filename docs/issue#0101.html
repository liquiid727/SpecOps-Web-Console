Implementation Notes

Issue #0101 — Fallback confirmation, cancellation, and concurrency safety — 2026-08-05

Design Decisions

Confirmation is an explicit state transition

Possible, confirmed, and unknown side effects enter awaiting_confirmation. A valid revision/token/input hash creates one confirmed-retry Attempt and clears the confirmation fields.

Bind in-flight idempotency to complete credentials

The coalescing key includes task, expected revision, confirmation token, and input hash. An invalid request cannot poison a concurrent valid request for the same task.

Preserve Task/Attempt consistency on cancel failure

If persisting Attempt cancellation fails, the coordinator does not continue to cancel the Task. The caller receives an explicit cancel failure and the active state remains recoverable.

Deviations

Restart retry remains blocked

The coordinator still keeps the executable request and runAttempt handler in memory. A new process can read a persisted Task but cannot safely execute its confirmed retry; this is not claimed as complete.

Tradeoffs

Strict API revision input

Missing, non-finite, fractional, and negative revisions are rejected before reaching the coordinator. This avoids ambiguous coercion at the HTTP boundary.

Local lock scope

Task locks and confirmation coalescing provide deterministic in-process behavior. Cross-process CAS/lock and fsync/crash semantics remain outside the verified boundary.

Open Questions

Safe restart context

Issue 102 must define the persisted, non-secret retry context or a recoverable terminal transition for awaiting-confirmation tasks after restart.
